## Decoding

| field | value | meaning |
| --- | --- | --- |
| `gdscr` | `0xf822f000` | UFS PHY GDSC powered; firmware left the power domain on |
| `axi` / `unipro` / `ice` | `0x221` | branch enabled (bit 0); hardware clock gating state is normal |
| `ahb` / `tx0` / `rx0` / `aux` / `aggre` | `0x1` | all UFS GCC branches enabled |
| `cap` | `0x1587031f` | UFSHCI 3.0 capabilities |
| `ver` | `0x300` | UFSHCI 3.0 |
| `hcs` | `0x10f` | host controller status: enabled, 64-bit addressing/UTP bits set |
| `hce` | `1` | **controller enabled** |
| `is` | `0x400` | one completion status pending |
| `ie` | `0` | interrupts masked |
| `utrlba` | `0xff12f000` | firmware request list (low 32 bits) |
| `utrlbau` | `0` | request list high bits |
| `dbr` | `0` | no doorbell outstanding |
| `rsr` | `1` | **request list running** |

**Conclusion:** the ABL/UEFI left UFS fully powered, clocked and running.
SM8450 GCC offsets in `Sm8450Platform/GccUfs.h` are correct. The driver can
adopt the live controller (`native-ufs-probe=3` style) and does not need to
program the QMP PHY or the GCC resets first.

## Port plan

1. Vendor the public `ShengUfs` driver as the build's `drivers/ShengUfs`
   component and apply a device patch that:
   - matches `qcom,sm8450-ufshc`;
   - uses `GCC_UFS_WINDOW 0x87000` with the SM8450 offsets
     (`gdscr 0x004`, `axi 0x018`, `ahb 0x020`, `tx0 0x024`, `rx0 0x028`,
     `unipro 0x064`, `ice 0x06c`, `aux 0x0a4`, `aggre 0x0d4`);
   - drops the SM8550 `GCC_UFS_MEM_PHY_GDSCR` (`0x9e000`) read (SM8450 has no
     separate UFS_MEM_PHY_GDSC);
   - keeps the UFSHCI transport, PRDT, SMMU stream `0x60`, and SHNGROOT window
     publication.
2. First build `native-ufs-probe=3` (adopt + read) and confirm the request
   list/SMMU path on cupid.
3. Then enable the root-window mode and flash the iOS 27 userdata image.

The six-image userdata image is already built and pinned
(`build/userdata-root.img`, `b6de4382…eb43`).

## Adopt/read test (build 43465529883, `266a62e`)

`patches/xnu/ufs-read.patch` adds `unixnu-ufs-read=1`. It maps UFSHCI
`0x1d84000`, reads the firmware request list from UTRLBA (`0xff12f000`), stops
the list, installs one COMMAND UPIU (TEST UNIT READY, LUN 0, no PRDT) at
list+4096, rings doorbell 0 and panics with OCS/response/SCSI, HCS, IS, DBR,
RSR and the first response words.

No SMMU writes: the UTRD/UCD/response all live in the firmware list region
that the controller's DMA already reaches. If the command does not complete,
the next step is the ShengUfs `smmuBypassStream(0x60, …)` plan/configure path.

## First read-test result

The first `boot-v4-ios27-ufsread.img` (build `43466961239`) aborted before the
TUR panic:

```
Unaligned kernel data abort at pc 0xfffffff00b43c3e8
far=0xfffffff92cb5a040  x0/x21=0xfffffff92cb5a000  x2=0x3f80
```

The invalid address is the `IOMemoryMap` of the firmware request list
(`0xff12f000`) plus `0x40`; the store was the first 16-byte `memset` write, and
the physical mapping rejects 16-byte stores. ShengUfs's `zero32` uses 32-bit
stores. `4c3f077` replaces `memset` with a volatile 32-bit loop; build
`43492154035` is the retry.

## Read test hung and reset (8eb8d70c)

The retry with 32-bit zeroing no longer aborted, but the phone did not reach a
panic screen. The video (22.9 s) shows the loader handoff for ~4.5 s, then a
black screen for ~17 s, then the Xiaomi boot logo — a watchdog reset, not a
kernel panic. The TUR command never completed.

Most likely cause: the controller could not DMA the replaced request list
because the UFS SMMU stream `0x60` was not bypassed. `ec7407e` adds
`patches/xnu/ufs-smmu.patch` (ShengUfs's `SmmuTakeover.h`, BSD-2 attribution)
and the read probe plans/configures the stream before writing UTRLBA. A SMMU
plan/readback failure now panics with the state instead of hanging.

Build `43499131082` is the retry.

## SMMU SError (e08298af)

With the SMMU bypass the phone panicked with "Unhandled implementation
specific error" (frames `0xb3c88e0 0xad2c08c 0xad2d874 0xb51543c 0xb02cb20
0xb3ac5f4 0xad325d0`), i.e. an SError from the SMMU path, not a TUR result.

The SM8450 `apps_smmu@15000000` is a `qcom,qsmmu-v500` (82 context banks,
133 SMRs, `handoff-smrs = <0x800 0x402>`), and the `ufshc@1d84000` vendor node
has **no `iommus` property**. The SM8550 ShengUfs SMMU writes are not safe to
apply blindly.

`a4532f6` removes the SMMU writes, issues START STOP UNIT power-active to the
UFS Device LUN `0xD0` (the device is likely in UFS-PowerDown), then TEST UNIT
READY, and panics with both results and UIC `0x38..0x4c`. Build `43505275141`
is the retry.

## SM8450 UFS SMMU stream is 0xe0

Mainline `arch/arm64/boot/dts/qcom/sm8450.dtsi`:

```
ufs_mem_hc: ufshc@1d84000 {
    compatible = "qcom,sm8450-ufshc", "qcom,ufshc", "jedec,ufs-2.0";
    iommus = <&apps_smmu 0xe0 0x0>;
    dma-coherent;
};
```

The SM8550 ShengUfs code bypasses stream **0x60**. On SM8450 that is another
master's stream, and configuring it is what raised the implementation-specific
SError. `e25eba0` re-adds the SMMU plan/configure with stream **0xe0** and
prints the UIC registers in the SMMU failure paths. Build `43510308708` is the
retry (with the SSU wake + TUR).

## Next: publish the windows

The remaining work is not another probe: the SHNGROOT windows must become
`IOBlockStorageDevice`/`IOMedia` objects the original APFS kext can attach to.
The sheng path (`NativeUfsBlock` + `SourceStorage.cpp`/`SourceRootPolicies.cpp`
+ signed policies) is the reference, but it is tied to sheng's device package
and iPad policies. For cupid:

1. Port the sheng SourceStorage runtime/block class (vendor the files from the
   public sheng repository, keep BSD-2 attribution) and adapt `NativeUfs` to
   SM8450: DT `qcom,sm8450-ufshc`, GCC window `0x87000` (SM8450 offsets),
   no `0x9e000` mem-PHY GDSC, SMMU stream `0xe0`.
2. Use the full `hostBringUp` (UIC link/power) rather than the firmware list;
   the transport already works, so this is mostly the existing sheng code.
3. For bring-up, bypass or generate the signed root policies (cupid iPhone
   pins are known; the sheng headers are iPad-only).
4. Flash `userdata-root.img` only after the windows can be read, because it
   overwrites Android `/data`.

## Patch-stack rebase and archive wiring (build 43579683881+)

The runtime patch is applied after every other series, and the arch series
(`offline-component-load-probes.patch`) puts the `#if DEVELOPMENT || DEBUG`
probe block immediately after `vfsinit()`. The regenerated hunk expected the
clean source (blank line then `#if CONFIG_PROC_UUID_POLICY`), so it failed at

used verbatim:

Two further wiring fixes before the archive step:

- `[kernel] archives` needs `component:ShengUfs`; on arm64e that recipe runs
  `build-sheng-source-storage.py --tree ROOT`, which finds the cupid policies
  under the copied `tree/scripts/policies`.
- `CONFIG_XNU_EXTRA_LD_ARCHIVES` must stay unset: `XNU_NATIVE_UFS=1` already
  force-loads `build/sheng-ufs/libShengUfs.a`, and the source-storage script
  copies its archive to that path. A second force_load would link the same
  objects twice (and the archive-plan check rejects the `-Wl,...` value).
- boot args are `native-source-storage=1 native-ufs-root=1` (the old
  `unixnu-ufs-read=1` probe argument is gone).


### Unverified publication gate

`NativeUfs.cpp` had one more owner-verification gate: the publication
`validate()` returned `false` in the `#else` branch ("Root publication
requires owner verification in every build"), so an unverified build could
never publish a window. For the cupid bring-up:

- `validate()` returns true and leaves the signed UUIDs empty;
- the publish thread's `wait()` returns immediately for an empty UUID instead
  of waiting 30 s for a signed identity that does not exist.

The windows are still started in the SystemOS-then-OS order; the original
APFS kext publishes the real volume UUIDs, and `IOFindBSDRoot` matches the
`/chosen/root-matching` UUID from the device tree. This path is bring-up
only; a verified build keeps the original gate.

### Unverified compile fixes

The verified implementation block also owns the transport timing helpers that
the shared read path uses (`timerTicks`, `native_ufs_read_ticks`), and the
stats/free paths reference `native_ufs_verified_blocks`,
`native_ufs_verify_ticks` and `native_ufs_integrity_failures`. `NativeUfs.cpp`
now defines those counters and `timerTicks` in a
`#if !NATIVE_VERIFIED_BLOCK` block next to the verified implementation, and
`SourceRootPolicies.cpp` guards its `read64` helper (used only by the policy
parser) the same way, so the bring-up build compiles with -Werror and without
the policy code.


### Minimal cupid runtime archive

The upstream source-storage archive compiles sheng's complete board-page and
diagnostic set (BootLog/BootUiTraceProbe/BootDiagExport/BootProcess*/Wifi/
Bluetooth). Those objects take the addresses of weak imports from sheng
components cupid does not select (`armcpu_spi_*`, `sheng_pmu_fixup`,
`native_adreno_*`, `native_gop_*`, `native_legacy_*`, `native_touch_*`,
`cs_*`, `vt_*`, `sheng_idle_*`, `ml_static_mfree_prepare`, ...). On arm64e
the address of such a weak import is an authenticated-pointer relocation and
is a hard link error even though the symbol is declared weak_import.

Cupid therefore ships a minimal runtime: the full diagnostic sources are
kept in `package/sheng-full/` and the top-level files are small stubs, so the
upstream build script still sees the names it compiles but the runtime only
contains NativeUfs/NativeRamBlock/SourceStorage/SourceRoot*/BootReset plus a
minimal BootLog state stub. The base ArmCpu already defines
`armcpu_spi_attach`, so `SourceStorage.cpp` supplies only the missing
`armcpu_spi_mask` (it must refuse so the transport stays in the polled mode
the read test proved) and `ml_static_mfree_prepare`, and
NativeUfs supplies a real `native_ufs_block_authenticates` that reports "not
a UFS window" in the unverified build. `log=1` is intentionally unavailable
(the manifest has no log window); the full sources can return when the sheng
board-page/GPU components are ported.
